WHAT IS THIS SYSTEM
System Overview
Khadmat AI is an AI-powered home services booking platform designed for Pakistan's informal economy. Customers describe what they need in Urdu, Roman Urdu, or English — and five AI agents handle everything from understanding the request to booking a provider and scheduling reminders. Providers get a full portal to manage jobs, earnings, and availability.
Core Insight This is NOT a simple listing/booking app. The central value is agentic automation — the AI understands natural language, finds the best provider, makes a decision, and confirms the booking without the user having to fill any form. The manual booking form exists only as a fallback.
Two distinct user roles
Customers book services. Providers receive and manage jobs. Both share the auth system but route to completely different dashboards after login.
Two booking modes
AI Chat (primary) lets customers type naturally. Manual Form (fallback) is a traditional step-by-step flow for users who prefer direct control.
Multilingual by default
The AI chat accepts Urdu, Roman Urdu, and English. The language.py utility detects which script/dialect is being used before passing to agents.
Agent trace as a feature
Every AI decision is logged and shown to the user in real time on the chat page. This is a transparency and trust-building feature, not just a debugging tool.
BACKEND / AI
Architecture & Agent Pipeline
The backend is a FastAPI server. When a customer sends a message, it passes through five agents orchestrated via Google Antigravity (ADK). Each agent has one job and hands off to the next.

Intent Agent
parse_intent()
Parses the message to extract service type, location, and preferred time. Handles Urdu, Roman Urdu, and English. Outputs structured JSON for the next agent.
Discovery Agent
search_providers()
Queries the providers table filtered by service category and area. Returns a list of available providers near the customer's location using haversine distance.
Decision Agent
rank_providers()
Scores each provider: distance + rating + availability. Selects the best match. Outputs top 2–3 for the UI to display, with the top choice pre-selected.
Booking Agent
create_booking()
Writes the booking to Supabase. Generates the BK-{date}-{id} reference. Marks the provider as unavailable for the booked slot. Returns confirmation data.
Follow-up Agent
schedule_reminder()
Inserts a reminder record into the reminders table for 1 hour before the appointment. In production, this triggers a WhatsApp/SMS/push notification.
Orchestrator
orchestrate.py
The Google Antigravity ADK chain that runs agents in sequence. Passes structured context between agents. Writes trace logs to agent_traces table after each step.
Loophole: Manual booking bypasses agents The manual booking form (page 3) does not call the AI agent pipeline at all. It writes directly to the bookings table. This means there are no agent trace logs, no AI decision, and no follow-up reminder automatically scheduled. The follow-up agent must be called separately even for manual bookings.

DATABASE
Data Model
Five Supabase tables power the platform. Understanding their relationships is critical before building any API endpoint.
providers
id
UUID primary key
name
Business/personal name shown on cards
category
AC Technician, Plumber, Electrician, etc. Used by Discovery Agent to filter
area / city
G-13, DHA, F-10 etc. Used with lat/lng for distance ranking
lat / lng
Coordinates for haversine distance calculation in distance.py
rating
Average rating 0–5. Updated after each review. Used in ranking formula
is_available
Boolean. Booking Agent sets this to false when a slot is booked. Must reset after job completes — this logic is NOT yet designed
bookings
id
UUID primary key
ref
Human-readable reference BK-{date}-{id}, generated by ref_gen.py
provider_id
Foreign key → providers. Links booking to a specific provider
user_id
Foreign key → users. The customer who made the booking
status
PENDING → CONFIRMED → COMPLETED or CANCELLED. Status drives all UI badge colors
scheduled_at
DateTime of the appointment. Reminder is set 1 hour before this
reminders
id
UUID primary key
booking_id
Foreign key → bookings
remind_at
scheduled_at minus 1 hour. A cron job checks this table and fires notifications
sent
Boolean. Prevents duplicate sends if the cron runs twice
agent_traces
session_id
Groups all agent steps from one chat session for the trace panel display
agent
Which agent ran: intent, discovery, decision, booking, followup
status
done / active / error
detail
Human-readable summary shown in the Trace panel
tool
The function call made, e.g. search_providers()
users
id
UUID, matches Supabase Auth user ID
name / phone / email
Core contact fields collected at signup
city
Default location for provider search. Customer sets this at signup
role
customer or provider. This single field determines which dashboard the user sees after login
Missing: reviews table Reviews are shown extensively across three pages (provider profile, reviews tab, full reviews page) but there is no reviews table in the schema. A reviews table needs: id, booking_id, provider_id, user_id, rating (1–5), comment, tags[], created_at.

Authentication — Login & Signup
1_auth_login_signup.html · /auth/page.tsx
Split layout (brand left, form right)
The left panel shows platform value props — roles, tagline — so users understand what Khadmat is before they sign up. This reduces drop-off by giving context before the form.
Role selection cards on signup
Customer vs Service Provider. Selecting Provider reveals extra fields (professions, experience, price range). This is the only moment the role field in users table is set — it cannot be changed later (no role-switch in settings).

Providers can tag multiple professions (AC + Electrician). This is important: the providers table needs a categories[] array or a many-to-many join table, not just a single category field.
Google OAuth button
Sign in with Google is shown but the signup form also collects phone number and city — data Google doesn't supply. A post-OAuth onboarding step is needed but not designed.
City selection at signup
Sets the user's default city (Karachi / Lahore / Islamabad). This populates the location field when the AI chat runs provider discovery, so users don't have to type their city every time.
Tab switching (Sign in / Create account)
JS toggles between login and signup views in the same page. The button label also changes ("Create account" vs "Join as provider") based on role selection.

⚠ Loopholes Found
Google OAuth users bypass city and phone fields — no post-OAuth onboarding page exists. City defaults to nothing, breaking the AI's location-aware search.
No OTP/phone verification step. Phone number is collected but not verified — fake numbers will be stored.
No password strength indicator on the signup form, though the placeholder says "Min. 8 characters."
Role cannot be changed after signup. If a customer wants to also become a provider, they need a second account.
Provider profession chips are cosmetic only in the design — the profession data must also seed the providers table correctly so the Discovery Agent can filter by it.
The "Forgot password?" link has no target page designed.

Critical Customer
AI Chat Booking
4_chat_booking_page.html · /book/page.tsx
This is the core feature. Every other page exists to support this one. The agent pipeline runs entirely from a message typed here.
Chat conversation UI
Two-column layout: chat on the left, agent trace panel on the right. Messages are streamed as the AI responds. Provider cards appear inline inside the AI bubble — not as a separate page.
Inline provider cards in AI bubble
After the Discovery + Decision agents run, the AI response contains ranked provider cards. The top match is pre-highlighted with a "best match" badge. The user can click to select a different provider before confirming.
One-message booking confirmation
User types "Ali ko book karo" and the Booking + Follow-up agents run immediately. The confirmation message shows the receipt inline — ref number, provider, time, reminder set — without leaving the page.
Agent trace panel (right column)
Shows all 5 agents with status (done/active/pending), what they did, and which tool they called. This is a real-time transparency feature — it makes the AI feel trustworthy by showing its reasoning.
Session info footer
Shows session ID, response duration (3.2s), model used (gemini-1.5-flash), and "All agents complete." This is useful for debugging but also reassures users that the system is fast and working.
Microphone icon in input
Suggests voice input support. This is not implemented in the design — no recording logic exists. Either remove it or implement voice-to-text before shipping.

⚠ Loopholes Found
There is no "View full receipt" button in the chat after booking is confirmed. The inline receipt is compact — users need a link to the full receipt page (/booking/[id]) to see the database state change panel and download the receipt.
If the user wants to change the time or provider after seeing the AI suggestion, there is no UI for that. The chat just shows a suggestion and "Ali ko book karun?" — but there is no way to edit the time slot without starting a new message.
The microphone icon implies voice input but nothing is wired up. Remove it or build it.
No multi-turn memory — each message is independent. If the user says "change the time to 3 PM" after a booking suggestion, the AI won't know what booking they're referring to unless session/conversation history is passed in every API call.
The trace panel is hardcoded to 5 agents always completing. A failed agent (network error, no providers found) needs an error state in the trace panel.
No loading/typing indicator while the agents are running (which takes 3.2s per the session info). Users will see a frozen UI for several seconds.

All Loopholes — Master List
Consolidated view of every gap and inconsistency found across the full design. Prioritized by impact.
Critical — Must Fix Before Demo
No reviews table in the DB schema, despite reviews being shown on 3+ pages. Add: reviews (id, booking_id, provider_id, user_id, rating, punctuality, value_for_money, comment, tags[], provider_reply, created_at).
Manual booking page (/book/manual) is not in the file structure — no Next.js route, no API handler defined.
The provider's is_available flag is set to false on booking but NEVER reset to true. After a job completes, the provider stays permanently unavailable. Need a "Mark complete" action or automatic reset at scheduled_at + estimated_duration.
No "Mark job complete" button on the provider side. Without it, bookings stay CONFIRMED forever and earnings cannot be finalized.
Providers with multiple professions: the current DB schema has a single category field, but the UI allows multi-select. Need categories[] (array) or a provider_categories junction table.
Manual booking does not call the agent pipeline — no reminder is automatically scheduled. The Follow-up Agent must be called explicitly for manual bookings too.
High Priority — Before Launch
Public provider profile page (/providers/[id]) — customers can't see a provider's full info before booking.
Rating/review submission flow — customers have no page to rate a completed job.
Google OAuth post-onboarding — no step to collect city and phone after signing in with Google.
Time slot availability API — manual booking's busy slots are hardcoded; needs GET /api/providers/:id/availability?date= endpoint.
Chat multi-turn memory — conversation history must be sent with every API call for context continuity.
Payout/withdrawal flow — completely missing. Provider earnings have no way to actually reach the provider's bank/JazzCash.
Booking cancellation confirmation dialog — one click cancels a booking with no warning.
Provider phone visibility — currently shown on New (pending) jobs; should only reveal after Accept.
Customer settings page — no place for customers to change their city, language, notifications, or password.
